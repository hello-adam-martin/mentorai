Learn Mentor, end to end

This is the long-form companion to the quick start. It takes you from the core idea all the way to a model running on a real engine — concepts first, then each of the seven layers in depth, then a hands-on tutorial, deployment, and a full reference.

In one sentenceMentor turns how your business should run into a small set of plain-Markdown files, then makes an AI engine operate inside those rules — handling the routine, escalating what matters, learning over time, and keeping people in control.

If you read top to bottom (using the Next button at the foot of each page) you'll move from why Mentor exists, through the ideas that make it safe, into the structure itself, and out the other side with a model you've built and deployed. Why Mentor

Most business software stores information and waits for you to act on it. Mentor flips that: it understands what's happening across the operation, coordinates the work, and brings you only the decisions that need a person.

The problem with normal software

A typical business runs on tools that follow one shape:

Data  →  UI  →  Human action

The software holds the records. You read the screens, hold the context in your head, chase the follow-ups, and make every call. That works when you're small. As you grow, the number of things to track grows faster than you do — and the tools don't help you decide anything, they just show you more. The chaos scales with the business.

The shift Mentor makes

Mentor is built around a different loop:

Intent → Reasoning → Coordination → Execution → Learning → Adaptation

Instead of being a place you go to do work, it's a layer that sits across the work. You tell it what the business is trying to achieve and the rules it must respect. It then reasons about what's happening, coordinates the routine itself, and surfaces the things that genuinely need you — with its reasoning attached, so you can trust or correct it.

The mental model that fits best is not "an app" but a capable operations lead who never sleeps and always works inside your rules.

What it actually does

  • Coordinates — routes work, chases follow-ups, keeps the moving parts in sync so nothing slips.
  • Remembers — builds lasting memory of your customers, jobs, quirks, and what worked last time. Institutional knowledge that sticks instead of leaving with whoever knew it.
  • Escalates — handles the routine on its own and brings the important decisions to the right person, fast.
  • Reasons — weighs options against what the business actually cares about, not just the loudest request.
  • Learns — spots recurring problems and proposes fixing the cause, so the same issue stops coming back.
  • Stays in its lane — acts only within the limits you set, logs why it did everything, and never crosses your bright lines.

It isn't tied to one industry

The structure is deliberately generic. The agents and the things they manage change between a café, a trades business, a clinic, or a holiday-rental operation — but the seven-layer shape stays the same. You're not buying a vertical product; you're describing your operation in a structure that any AI engine can run.

Where this is headingThe long-term aim is an operational layer that sits across a real-world business — not a CRM, not a PMS, not workflow software, but a living layer that understands, coordinates, and helps people decide. The next pages explain the ideas that make that safe to actually switch on.

The seven-layer model

Mentor organises a whole business into seven layers. Intent and authority flow down; state and outcomes flow up. That single picture is most of the system.

The layers at a glance

#LayerAnswersRole
1StrategyWhat is the business trying to achieve?intent
2GovernanceWhat may it do alone, and what are the lines it never crosses?guardrails
3LearningHow does it get better over time?improvement
4CoreWhat reasons and decides?the engine
5Domain agentsWho does the work?the doers
6Operational objectsWhat real things does it coordinate?the nouns
7Human collaborationWho approves, oversees, and steps in?in charge

Why a hierarchy

The layers above define — goals, permissions, constraints, learning. The layers below perform — execution, coordination, the actual operational work. A decision made low in the stack (an agent acting on an object) is always bounded by the layers above it (the governance rules, the strategic priorities). This is what stops a capable system from being a dangerous one.

Seven files, one graph

The layers aren't islands. They reference each other by shared names, and those cross-references turn seven separate descriptions into a single connected model:

  • Strategy owns the objectives.
  • Governance's actions reference objectives via serves — every action exists to advance something.
  • Domain agents reference the actions they're allowed to perform, and the object types they touch.
  • Operational objects define the entity types the agents act on.
  • The Human layer references the approvers Governance names — mapping a rule to a real person.
  • Learning references objectives, objects, and actions — what it watches, what it protects, what it would change.

Because of this, a model isn't valid just because each file is well-formed — it's valid when every reference resolves. That's what the validator checks, and it's covered in the spec format.

You don't need all seven to start

A viable first slice is Strategy + Governance + one Domain agent — intent, the rules, and one specialist that honours them. The other layers can sit at status: planned and be filled in as you need them. The architecture is built to be grown incrementally, not authored all at once.

Coming upEach layer gets its own deep-dive page later. First, the five concepts that explain why the layers are shaped the way they are.
Core concepts

Built around intent, not forms

Traditional software makes you drive every screen. Mentor works backwards from what you're trying to achieve — so you state the goal, and it figures out the steps.

What "intent-first" means in practice

In a normal tool, the unit of work is a form: a booking form, a ticket, a record to update. The software is neutral about why you're filling it in. With Mentor, the first thing you define is the business's objectives — weighted and measurable — and everything below answers to them. An action isn't just "a thing the system can do"; it's a thing that exists to serve one or more objectives. An agent isn't a feature; it's a specialist scoped to advance specific goals.

Why this matters when options compete

Real operations are full of trade-offs. Approve the early check-in (happier guest, more cleaner pressure) or hold the line (calmer operation, slight review risk)? A form-based tool has no opinion — it just records whatever you decide. Mentor scores each option by how much it advances your objectives, weighted by how much each one matters, and prefers the best permitted option. The weights you set are what break the tie.

The ruleWhen options are genuinely close, the system does not guess — it escalates to a human. Intent guides the decision; it never overrides a governance rule or skips a required approval.

Intent must be measurable

An objective without a target is a slogan. "Great customer experience" can't be judged; "average review rating ≥ 4.5 stars" can. Mentor insists each objective carries a measurable target, so the system is held to outcomes, not activity. This is also what lets the Learning layer later tell whether a change actually helped.

The next concept is the other half of safety: even with clear intent, the system only earns the right to act on its own gradually.

Core concepts

Autonomy is earned

Nothing starts trusted. Every action the system can take carries one of three autonomy tiers, and actions migrate toward independence only as evidence shows they're safe.

The three tiers

auto

Do it now, and log why. Reserved for reversible, low-risk, well-understood actions.

recommend

Propose it and wait for a yes before acting. The safe default for almost everything new.

approve

Do nothing until a named person explicitly signs off. For anything irreversible, financial, or sensitive.

If an action isn't clearly granted as auto, the system treats it as recommend. Caution is the default state, not something you have to remember to switch on.

Start cautious, loosen on evidence

The guiding economics: it's cheap to grant more autonomy later; it's expensive to undo a bad automatic action. So a new model puts new actions at recommend, keeps money, deletion, and public statements behind approve, and only promotes an action to auto once the Learning layer shows it has been consistently right.

The autonomy migration

Promotion is a deliberate, reversible edit — not something the system does to itself:

  1. An action has run at recommend for a while and you've been saying yes every time.
  2. You edit the Governance Markdown to move it recommend → auto.
  3. Re-validate, re-compile, reload the engine.

This is exactly the loop the Governance and Learning layers were built for. And it runs the other way too: if an auto action starts misbehaving, you demote it with the same edit.

A tier is only as strong as its enforcementWriting "this needs approval" in a prompt is guidance, not a guarantee. At deployment, an approve tier must be backed by real approval gating, and a hard limit by a hook or by withholding the tool entirely. More on this in Engine-agnostic & adapters and the Deploy page.
Core concepts

Humans in the loop

Mentor is explicitly not designed to remove people. It's designed to reduce their load and sharpen their decisions — humans stay the approvers, supervisors, and the final word.

What changes, and what doesn't

What changes is the noise: the routine coordination, the chasing, the holding-it-all-in-your-head. What doesn't change is who's in charge. People remain the approvers (money, sensitive calls), the supervisors (watching the decision feed), the experts (the source of truth the system defers to), and the escalation handlers (the person an emergency reaches).

The loop, concretely

Human-in-the-loop isn't a slogan here; it's wired into the structure. Governance names approvers by role. The Human Collaboration layer maps those approver roles to real people, with the channels they're reached on. So when an approve-tier action comes up, there's an unambiguous path from "this needs sign-off" to a specific person's phone.

Design intentThe system exists to surface the right decisions to the right person at the right time — not to make more decisions on its own. When in doubt, it surfaces rather than acts.

Explainability is part of the contract

Every action records which objective it served and the reasoning behind it, in plain language a person could review later. A decision that can't be explained simply is treated as a governance failure, not a clever shortcut. This is what makes oversight real rather than theatrical: you can actually read why the system did what it did.

No blind loops

If the system fails the same task repeatedly, or two agents disagree, it doesn't keep trying — it stops, logs its reasoning, and escalates to a human. Persistence is not a virtue when you're stuck; getting the right person involved is.

Core concepts

Engine-agnostic & adapters

Your operating model never names a specific AI engine. It references a small vocabulary of abstract capabilities, and a swappable adapter maps those onto whatever engine you actually run. Change engines by changing the adapter — not by rewriting your model.

Why the separation exists

AI engines evolve fast and differ a lot. If your operating model were wired to one engine's features, you'd be locked in, and every engine change would mean re-authoring everything. Mentor avoids that by splitting binding into two pieces: an abstract contract (what any engine must provide) and a per-engine adapter (how a particular engine provides it). Your seven layers only ever reference the abstract contract.

The capability vocabulary

The abstract contract is a short list of capabilities an engine must offer:

CapabilityWhat the engine must provide
durable_contextpersistent instructions present in reasoning every session
identitythe agent's standing voice / disposition
fact_memorysmall, always-on facts in working context
knowledge_storelarger queryable memory of entities, history, relationships
procedurea reusable, loadable unit of know-how
agentan addressable worker that can be delegated to
scheduletime- or event-triggered autonomous runs
enforcementability to gate, require approval for, or block an action
channela path to reach and be reached by humans
enginethe reasoning loop that consumes the above and decides

Binding is mostly placement

Because a Mentor model is already Markdown, "binding" to an engine usually isn't a format conversion — it's deciding which loader each file is fed into. A layer's .md becomes a context file, a memory note, a skill, a scheduled job, or a channel config. There's no compiler magic; there's placement.

Worked example: Hermes AgentThe adapter for Hermes Agent maps durable_context → its AGENTS.md context file, procedure → SKILL.md skills, schedule → cron jobs, channel → its messaging gateway, and so on. Switching to a different engine means writing a new adapter table — the layer files don't move. See the Engine adapters reference for the full map and a step-by-step deployment play.

The honest caveat about enforcement

Not every engine enforces business rules natively. Hermes Agent's built-in approval, for instance, targets dangerous shell commands — not "don't issue a refund." So the adapter's job includes noting where you must back a rule with a hook, or by simply not giving the agent the tool or credential in the first place. The strongest limit is a capability the agent doesn't have.

Core concepts

The Markdown spec format

Every part of a Mentor model is a Markdown file. The structure is a folder tree, the source of truth is YAML frontmatter, and a validator checks that the whole thing holds together. No database, no proprietary format, no compiler.

A folder is a node

The model is a folder tree, and the convention is simple:

  • A folder is a node. Its node file is named after the folder — Objective1/Objective1.md.
  • The numbered top-level layers drop the number on the file: 1_StrategicLayer/StrategicLayer.md.
  • Layer overviews live in the layer folder's own node file; components are sub-folders.
  • Ids are lowercase_snake_case; folder names are PascalCase.

This mirrors the "zoom" idea — you can open the model at any level — and it's engine-native, because engines that walk directories pick up per-folder context naturally.

Frontmatter is canonical; prose mirrors it

Each node file is YAML frontmatter (the machine-checkable source of truth) followed by a Markdown body (prose plus light tables) that mirrors it for human reading. If the two ever disagree, the frontmatter wins. Here's a real objective node:

---
mentor_node: objective
layer: strategic
id: customer_experience
label: "Customer Experience"
weight: 0.4
targets:
  - { metric: "avg_review_rating", operator: ">=", value: 4.5, unit: "stars" }
guidance: "Favour the guest when a complaint is borderline."
---

# Customer Experience
Fast, friendly service and consistent quality that keeps regulars loyal.

Validation: the model as one graph

A model is correct when every cross-layer reference resolves, not just when each file parses. The validator (built into Mission Control, and mentor validate on the command line) checks invariants like:

  • Objective weights sum to 1.0, and each objective has a valid target.
  • Every approve-tier action names a real approver; every serves resolves to an objective; every escalates_to resolves to a known action.
  • Each operator's fulfils_approvers resolves to an approver Governance defined.
  • Every object relationship's to resolves to another object type; every agent's actions and objects resolve.
  • Audit logging and required reasoning are on.
Why Markdown specificallyMarkdown is the universal substrate for agent context, memory, and skills across every engine. A Mentor spec needs no compiler and drops into any engine. It's readable by you, by any engine, and checkable by a tool — and it's yours, with no lock-in.

The full field-by-field definition for every node type is in the Spec format reference.

The seven layers · 1 of 7

Layer 1 — Strategy

What the business is trying to achieve, expressed as a handful of weighted, measurable objectives. This is the layer everything else answers to.

What it is

The Strategic layer holds the business's intent: a short list of objectives, each with a relative weight (how much it matters) and a measurable target (how you'll know it's working). It also carries the mission statement and the trade-off policy for close calls. When the system weighs competing options, it scores them against these objectives — so this layer literally shapes every downstream decision.

Why it exists

Without stated intent, automation is just activity. The Strategic layer is what lets the system prefer the option that advances the business rather than the one that's loudest or easiest. The weights matter most precisely when objectives compete — and in a real operation they always do.

How to fill it well

  • Choose 3–5 objectives that genuinely trade off. If two objectives never pull against each other, you don't need to weight them separately.
  • Make the weights sum to 1.0. They're shares of importance, and they decide who wins a close call.
  • Give each a measurable target with a metric, operator, and value — avg_review_rating >= 4.5, not "be excellent".
  • Resist the long list. A handful you actually mean beats fifteen you don't. Five competing priorities is plenty for a system to balance.

A worked snippet

A café might weight three competing goals like this — note they sum to 1.0:

customer_experience  (0.40)  target: avg_review_rating >= 4.5 stars
profitability        (0.35)  target: food_cost_pct      <= 30 %
low_waste            (0.25)  target: food_waste_pct      <= 5 %

Each lives in its own folder (1_StrategicLayer/Objective1/) as a node with id, label, weight, targets, and optional guidance (e.g. "favour the guest when a complaint is borderline").

Common mistakesWeights that don't sum to 1.0 (the validator will flag this); objectives with no measurable target; or a wish-list of ten objectives that never actually compete — which gives the system nothing to balance and you no real priorities.
The seven layers · 2 of 7

Layer 2 — Governance

What the system may do on its own, what needs a human's yes, and the lines it must never cross. This is the most important layer for safety — and the one to get right before you grant any autonomy.

What it is

Governance defines authority. It contains actions (each with an autonomy tier), approvers (who can sign off), hard limits (absolute prohibitions), escalation rules (when to pull a human in fast), notifications (quiet hours), and audit settings. Crucially, Governance supersedes Strategy: a strategic weight can influence which permitted option is preferred, but it can never authorise something a hard limit forbids or skip a required approval.

Actions and their tiers

Each action declares a tier — auto, recommend, or approve — the objectives it serves, the domains it belongs to, its conditions, and (for approve) the named approver and any limits. Two real café actions:

# reorder_stock — tier: auto
serves: [profitability, low_waste]
conditions: "within par levels and approved suppliers only"

# issue_refund_or_comp — tier: approve
serves: [customer_experience]
approver: owner
limits: { max_cost: { amount: 50, currency: "NZD" } }

Reordering within set par levels is reversible and routine, so it's auto. Refunding money is sensitive, so it's approve, capped, and routed to a named approver.

Hard limits — the bright lines

Hard limits are a short list of genuine prohibitions that nothing overrides — no objective, deadline, or urgency. Keep the recommended starter set and add your own:

  • Never move money, issue refunds, or change payouts without approval.
  • Never share personal or customer data with third parties without approval.
  • Never make legally binding commitments or public statements as the business without approval.
  • Never permanently delete or irreversibly destroy records without approval.
  • Always disclose that you are an AI when asked.

How to fill it well

Start cautious. Put new actions at recommend; reserve approve for anything irreversible, financial, or sensitive; only mark something auto when it's genuinely reversible and low-risk. Name real approvers. Keep audit on (log_all_actions and require_reasoning must both be true — the validator enforces it; how that logging actually works at runtime is covered in Wiring the guardrails). Define at least the two default escalations: a safety/legal emergency reaches a human immediately, and repeated failure stops and escalates rather than retrying blindly.

Common mistakesMaking things auto to "save clicks" before they've earned it; bright lines so numerous they stop being bright; or an approve action with no approver named (invalid). Remember: a tier or limit written in text is only a guarantee once it's backed by enforcement at deploy time.
The seven layers · 3 of 7

Layer 3 — Learning

How the system improves over time: spotting recurring problems, getting ahead of risk, and testing changes before they ship. This is what turns automation into adaptive operational intelligence.

What it is

The Learning layer holds three kinds of node:

  • Patterns — recurring things to watch for. A pattern detects something, watches the object types whose history reveals it, and suggests an improvement to propose.
  • Predictions — risks to get ahead of. A prediction predicts a metric or outcome over a horizon and informs the objectives it helps protect.
  • Simulations — what-ifs to test before changing how an action is used. A simulation describes a scenario, compares options, scores_against objectives, and notes the affects_actions it would change.

Why it exists

It's the layer that closes the loop. Outcomes flow back up; the Learning layer notices the recurring issue and proposes fixing the cause rather than handling the symptom again. It's also where the evidence for autonomy promotion comes from — an action earns auto because Learning shows it's been consistently safe.

A worked example

From the original vision: guests keep getting confused about parking. A pattern watching booking and guest history detects the recurring complaint and suggests updating the check-in guide with annotated arrival photos. A simulation can weigh "approve early check-in" (+guest satisfaction, −cleaner pressure) against "deny" (+operational stability, −review risk) before you change how that action behaves.

How to fill it well

It's optional at first — leave it light. As you actually notice recurring problems in the running system, add a pattern. As a risk becomes worth pre-empting, add a prediction. Before changing an action's tier or conditions in a way you're unsure about, sketch a simulation. Don't try to predict every problem up front; let real operation tell you what's worth watching.

TipLearning is where scheduled reviews and briefings live once deployed — the engine's cron runs them. Pair it with audit: the decision log is the raw material the Learning layer mines.
The seven layers · 4 of 7

Layer 4 — Core

The reasoning engine that ties everything together — builds context, scores options against intent, and routes work within authority. It's the one layer you choose rather than author.

What it is

Core is the operational brain. It doesn't do all the work itself; it coordinates. Its responsibilities are orchestration, memory access, context building, agent coordination, prioritisation, decision routing, and escalation management. In Mentor terms: it consumes Strategy and Governance, delegates to Domain agents, acts on Operational objects, and pulls in Humans when the rules say to.

Why there's nothing to write here

Unlike the other six layers, the Core layer has no authored content. It is the AI engine you decide to run on — so it's configured through an adapter, not described in node files. The 4_CoreLayer/ folder exists as a placeholder; what fills the role is the engine itself (its reasoning loop and prompt builder), set up at deployment.

Leave it open until deploymentKeep engine_adapter: null until you decide where to run. Mentor is engine-agnostic by design — choosing the engine is a deployment decision, not a modelling one. See Engine-agnostic & adapters.

How Core uses the layers at runtime

When the system runs, Core reasons inside the Strategy, bounded by Governance, delegating to Domain agents, acting on Operational objects, and escalating to Humans. The launch prompt is what configures the engine to behave this way — it bakes in Strategy and Governance and tells the engine to consult the other layers on demand. That prompt is covered on the Deploy page and in the Launch prompt reference.

The seven layers · 5 of 7

Layer 5 — Domain agents

The specialists that do the actual work, grouped into domains. Each agent is deliberately narrow — scoped to a few allowed actions and the object types it touches.

What it is

Below Core sit operational domains — typically Operations, Intelligence, and Communication — and inside each domain live agents. An agent declares its domain, a purpose, the allowed_actions it may perform (a subset of Governance actions), and the objects (object types) it reads and writes. It can also carry an optional friendly name — a persona like "Frankie" — that shows up in the map and the compiled skill, so a running system feels like a named team.

Why agents are scoped

A narrow agent is a safe, debuggable agent. Because each agent can only perform its allowed actions on its object types, authority is contained: a Communication agent that handles guest messages simply has no path to reorder stock. Scope is also how you reason about a deployment — you wire up tools and data for one agent's remit at a time.

A worked snippet

id: front_of_house_agent
name: "Frankie"
domain: operations
purpose: "Keep stock at par and propose daily specials from demand."
allowed_actions: [reorder_stock, adjust_daily_specials]
objects: [customer, order, menuitem]

Frankie can only do the two actions listed, only on those object types. Everything else is out of remit by construction.

How to fill it well

  • Start with one agent. Strategy + Governance + one scoped agent is a complete first pass — you can add more later.
  • Keep each agent's action set small and tied to a clear job. If an agent does "everything", split it.
  • Prefer a single owner per action. The builder gives a soft warning if an action is owned by more than one agent — it allows deliberate overlap (e.g. guest messaging), but a single owner means clear accountability and routing.
  • Only list the object types the agent really touches — that's also the data you'll have to connect at deploy time.
Common mistakesOne mega-agent with every action; agents referencing actions or object types that don't exist (the validator catches this); or wiring up ten agents before a single one has proven itself in a pilot.
The seven layers · 6 of 7

Layer 6 — Operational objects

The real-world things your business revolves around — customers, jobs, properties, orders — modelled as living record types that carry their own history.

What it is

Operational objects are the nouns of your operation. Each object type declares a stable key (its identifier field), the fields that matter, relationships to other types, optional lifecycle states, and history: append_only so its past is never silently rewritten. At runtime these become "living nodes" that accumulate memory, history, relationships, and operational state — the institutional intelligence the system reasons over.

Types, not instances

The key distinctionThis layer models types, never instances. You define "Customer" — not "Jane Smith". The actual records (the instances) are live data connected at deployment, living in the engine's knowledge store. The spec defines the shape; the engine holds the contents.

A worked snippet

id: customer
label: "Customer"
key: "customer_id"
fields:
  - { name: "full_name", type: "text" }
  - { name: "email", type: "text" }
  - { name: "loyalty_points", type: "number" }
relationships:
  - { type: has_many, to: order }
states: [new, regular, lapsed]
history: append_only

Here a Customer has_many Orders — and that to: order must resolve to another object type defined in this same layer, or validation fails.

How to fill it well

  • Model only the few entities the business genuinely revolves around. A café needs Customer, Order, MenuItem — not a full schema of every table you'll ever store.
  • Give each a stable key and only the fields that actually inform decisions.
  • Use relationships to connect types — and remember complex links (an Order joining a Customer and a Product) are modelled as their own type when needed.
  • Don't try to load data here — that's deployment, not modelling.
The seven layers · 7 of 7

Layer 7 — Human collaboration

The real people who approve, oversee, and step in — mapped to the approver roles Governance named. This is the layer that closes the loop between "needs a person" and an actual person's phone.

What it is

The Human Collaboration layer holds operators — one per person or role. Each operator declares a name, a role, the channels they're reached on, what they handle (their responsibilities), optional availability, and — most importantly — fulfils_approvers: the list of Governance approver ids this person is.

Why it's a separate layer

Governance names approvers as roles ("owner", "shift_lead") so the rules stay stable even as people change. The Human layer binds those roles to real individuals and their contact channels. Separating the two means you can swap who fills a role without touching your governance rules — and it's what makes an approve-tier action actually reach someone.

A worked snippet

id: owner_jane
name: "Jane"
role: "Owner"
fulfils_approvers: [owner]      # maps to the Governance approver "owner"
channels: [telegram, email]
handles: "Refunds, owner payouts, anything financial or sensitive"

Not everyone is an approver. An on-call handler who only receives escalations has an empty fulfils_approvers — they're in the loop without holding sign-off authority.

Common mistakesAn operator's fulfils_approvers referencing an approver id that Governance never defined (invalid — the validator checks this); or naming approvers in Governance with no real person mapped to them, leaving an approval path that dead-ends.

Build & deploy

Tutorial: your first model

We'll build one complete, runnable model from scratch — a small café called Riverside Café — touching every layer. By the end you'll have a validated business folder you can compile and deploy. Allow about 30 minutes.

What you'll useOpen Mentor Studio in another tab. It walks you through each layer with plain-English help and pre-fills safe defaults, then maps, validates, and compiles — all in your browser, nothing uploaded. (Prefer the terminal? mentor new riverside-cafe scaffolds the same starter folder.)

The plan

You don't need all seven layers to have something real. We'll do the complete set, but the spine is Strategy → Governance → one agent. Studio orders the steps by dependency: Strategy, Governance, Objects, Domain, Human, Learning, then Core (which you just choose later).

Step 1 — Strategy: what matters

Riverside has three goals that genuinely compete: delight customers, stay profitable, and cut waste. Give each a weight that sums to 1.0 and a measurable target.

customer_experience  (0.40)  avg_review_rating >= 4.5 stars
profitability        (0.35)  food_cost_pct      <= 30 %
low_waste            (0.25)  food_waste_pct     <= 5 %

In Studio's Strategy step, add three objectives, set the weights, and give each a target. Add a line of guidance where it helps — for customer experience, "favour the guest when a complaint is borderline."

Why these threeThey pull against each other — comping a dish helps experience but hurts profit. That tension is exactly what the weights resolve. If your goals never trade off, you have fewer real objectives than you think.

Step 2 — Governance: what it may do

Now decide, for each thing the system might do, how much rope it gets. Keep the pre-filled safe defaults and add café-specific actions:

ActionTierWhy
reorder_stockautoReversible, within set par levels and approved suppliers.
adjust_daily_specialsrecommendLow-risk but worth a glance before it posts.
issue_refund_or_compapproveMoney — routed to the owner, capped at $50.

Name your approvers (owner, shift_lead). Keep the starter hard limits (no moving money / sharing data / public statements / irreversible deletes without approval; always disclose it's an AI) and add one of your own: "never serve or advertise an item without disclosing its known allergens." Keep both default escalations and leave audit on.

Step 3 — Operational objects: the nouns

Model only what the café revolves around. Three types is plenty:

  • Customer — key customer_id; fields like name, email, loyalty points; has_many orders; states new / regular / lapsed.
  • Order — what was bought and when.
  • MenuItem — the menu, with allergens and cost.

Remember you're defining types, not loading real customers — the records come at deployment.

Step 4 — Domain agents: who does the work

Start with one well-scoped agent and add two more for a fuller picture:

Frankie — Front of House (operations)
  actions: reorder_stock, adjust_daily_specials
  objects: customer, order, menuitem

Gail — Guest Relations (communication)
  actions: issue_refund_or_comp, reply_to_review
  objects: customer, order

Iris — Insights (intelligence)
  actions: send_weekly_report — surfaces trends
  objects: order, menuitem

Each agent can only perform its listed actions on its listed object types. If you assign one action to two agents, Studio shows a soft "shared action" warning — fine if deliberate, worth a look otherwise.

Step 5 — Human collaboration: who's in charge

Map the people to the approver roles you named in Governance. Jane (the owner) fulfils_approvers: [owner] on Telegram and email; the shift lead fulfils shift_lead. Add an on-call handler with an empty approver list — in the loop for escalations, but not an approver.

Step 6 — Learning (optional)

Leave this light for a first model. You might add one pattern — "guests repeatedly ask about gluten-free options" → suggest flagging GF items on the menu — but it's perfectly fine to skip Learning until the running system shows you what's worth watching.

Step 7 — Map & validate

Switch to Studio's Map & validate tab. You'll see the whole model as a hierarchy; click any box to inspect its full definition. Confirm the validation panel is green: weights sum to 1.0, every serves/approver/relationship/agent reference resolves, audit is on. Fix anything red before continuing — a model with a dangling reference will misbehave when it runs.

Step 8 — Compile & download

On the Compile & download tab, hit Download (ready to run). You get one self-contained folder containing your seven layers, the launch prompt (AGENTS.md) with your mission, objectives, approvers, hard limits, and escalations baked in, a SKILL.md per agent, a SETUP.md checklist, and a DEPLOY.md guide — plus Mission Control, so the folder travels with its own map.

You're done modelling 🎉That folder is your business. Coming back later? In Studio, use Import an existing folder to re-open it and edit any step. Now let's make it actually run.

Step 9 — Deploy on Hermes (the complete worked setup)

This is where the café stops being a folder and starts running — with the guardrails actually enforced, not just described. The runnable kit is a business-neutral adapter at adapters/hermes/ that you copy next to your model. It has no copy of your rules: the plugin reads them live from your Governance layer, so editing the Markdown changes enforcement with nothing to regenerate. example/deploy/hermes/ is that adapter copied for the café — and it carries no rules file at all. (Engine specifics live in an adapter, never in the engine-neutral model — see Engine-agnostic & adapters.)

Build & deploy

Deploy & go live

This is where the agents stop being descriptions and start existing. Modelling was thinking; deployment is software and integration work. Do it for one agent's scope only, and keep everything at recommend to start.

The launch prompt does the thinking; three things let it act

The compiled AGENTS.md is the bootstrap that makes a general AI engine behave as Mentor: it bakes in your Strategy and Governance and tells the engine to consult the other layers on demand, weigh options against your objectives, respect the tiers, never cross a hard limit, and escalate when unsure. But behaving isn't acting. To let it actually do things, the engine needs:

  • Tools — wired to real systems, so an agent can send a message, create a task, or update a record.
  • Data — your Operational Objects connected to where the live records actually live (inbox, scheduler, CRM/PMS). The spec defines the types; the engine needs the instances.
  • Enforcement — hard limits and approve tiers backed by engine hooks or by withholding tools/credentials. Stated-in-text rules are guidance; a hook is a guarantee.

Prerequisites

A validated model and a fresh compiled bundle; somewhere to run it (a small VPS, or your own machine for a pilot); an engine plus a model-provider API key; credentials for one channel (Telegram is quickest); and read access to the one system your pilot agent will touch.

The six deployment steps

  1. Stand up the engine. Install it, configure provider/model/key, confirm it replies to a plain chat. (This is your Core layer — configured, not authored.)
  2. Load the model. Put AGENTS.md in as the context file with the operating-model folder beside it; drop the agent skills into the engine's skills directory; seed a few always-on facts into memory. Test: ask it "what are you optimising for?" — it should answer as Mentor, with your objectives and weights.
  3. Connect one channel so approvals and escalations reach you and you can talk to it. Verify a round-trip.
  4. Give it hands — connect the minimum tools the pilot agent needs, and its in-scope object data, read-only against the system of record first. Don't wire everything.
  5. Wire the guardrails — route approve-tier actions through real approval; back each hard limit with a hook or by withholding the tool/credential entirely (the strongest limit is a capability the agent doesn't have); confirm audit logging is on. This is the crucial step — see Wiring the guardrails for the full how-to.
  6. Pilot. One objective, one agent, one channel, a slice of real data, everything at recommend — it proposes, you confirm by hand. Agree success criteria and a review window up front, and watch the decision feed.
The deploy folder is self-containedThe "Download (ready to run)" ZIP is your business folder, with AGENTS.md inside it next to the layers. Deploy flow: unzip → cd into the folder → start your engine there (it finds AGENTS.md in the working directory and reads layers on demand) → copy skills/ into the engine's skills directory. The DEPLOY.md inside lays out every step.

Worked example: Hermes Agent

The Engine adapters reference maps every Mentor capability onto Hermes Agent and includes a complete step-by-step "Hermes Agent on WSL" play for running a pilot on a Windows machine — installing WSL2, standing up the engine, loading the model, connecting Telegram, wiring guardrails, and keeping it always-on. For another engine, the adapter table is the place to start.

Wiring the guardrails

This is the step that turns your model from a blueprint into a system you can safely switch on. Everything else describes what should happen; guardrails are what make it actually happen.

The whole idea in one lineA stated rule is guidance; an enforced rule is a guarantee. A hard limit is only as strong as its enforcement — bright lines are "absolute" only if something other than the model's good intentions makes them so.

Why the prompt isn't enough on its own

The launch prompt makes the engine intend to obey — it knows the tiers, the hard limits, and the escalation rules, and a good model follows them most of the time. But "most of the time" isn't the bar for moving money or sharing customer data. An AI agent can be wrong, get confused by an edge case, be talked out of a rule by a clever message, or hallucinate a tool call. Instruction text is a strong prior — not a wall. You're guarding against two failure modes: acting when it shouldn't (crossing a hard limit) and acting without the required sign-off (an approve action with no real approval).

The four mechanisms, strongest first

Prefer the strongest mechanism available for each rule, and layer them:

  1. Withhold the capability (strongest). Don't give the agent the tool or credential at all. An agent with no payments key cannot move money, whatever it reasons. The strongest limit is a capability the agent simply doesn't have.
  2. Gate behind approval. Route the action through a real human confirmation before the tool executes — the agent proposes, a named person confirms in a channel, only then does it run. This is how every approve-tier action should work.
  3. Hook / interceptor. A check that runs just before a tool call and can block or escalate based on rules — an amount threshold, a recipient allow-list, message content. This enforces conditional limits like "refunds over $50 need approval".
  4. Audit (detective, not preventive). Log every action, its reasoning, and the objective served. It doesn't stop a bad action, but it makes one visible and reversible — and it's how you catch a guardrail that's quietly stopped working.
Default posture: withhold by defaultStart the pilot agent with the minimum tools and read-only data. Grant write or destructive capability only when a specific action needs it — and gate it when you do. "It can't do the wrong thing because it has no way to" beats "it knows not to" every time.

Map each rule to how it's enforced

Most hard limits collapse to "don't give it that capability" plus a hook for the conditional cases. The behavioural rules are the only ones you genuinely can only nudge in text and verify in audit:

RuleHow you enforce it
No moving money / changing payouts without approvalWithhold the payments credential; gate any payout tool
No sharing customer data with third partiesWithhold/scope export tools; hook to block external recipients
No irreversible deletesWithhold destructive scope; soft-delete only
No public statements as the businessWithhold posting credentials; gate if granted
Always disclose it's an AIBehaviour — prompt + audit spot-check, optional outbound hook
An approve action (e.g. a capped refund)Gate to the named approver + hook to enforce its limit

Test them — try to break them

A guardrail you haven't tried to break is one you don't haveBefore the pilot goes live: red-team each hard limit by explicitly asking the agent to do the forbidden thing and confirming it's blocked — not just that it politely declines (a decline is the prompt working; a block is the guardrail working). Round-trip an approve action to confirm it pauses and reaches the approver's channel. Push an amount just over a threshold and confirm the hook stops it. Confirm audit records the reasoning.

How the automatic logging works

Audit is the guardrail you'll lean on constantly, and it works in two parts. The model declares the policy — one Governance node sets it:

mentor_node: audit
log_all_actions: true
require_reasoning: true
retain_days: 365
human_reviewable: true

That's a policy, not a running logger: every action recorded, each one carrying its reasoning (which objective, and why), kept ~365 days, human-reviewable. The engine does the actual logging at runtime, in two moves — it generates the reasoning as it acts (the launch prompt tells it to record the objective served and a plain-language reason for every action: "if you can't explain it simply, don't do it"), and it persists that record in its own memory (on Hermes Agent, the SQLite session store plus the decision feed).

Two things to hold onto. It's detective, not preventive — it doesn't stop a bad action, it makes one visible and reversible, which is why it pairs with the mechanisms above rather than replacing them. And the validator refuses to pass a model unless log_all_actions and require_reasoning are both true, so the policy can't be switched off by accident — though, as ever, a prompt instruction is only guidance until the engine's native logging backs it (confirm it's on at deploy). That log is also what earns an action its promotion to auto and feeds the Learning layer.

On Hermes Agent (the worked example)

Key caveat: Hermes's native approval targets dangerous shell commands, not business rules — so don't rely on it to stop "issue a refund". Enforce business limits via hooks and tool-gating. Take the café's capped, owner-approved refund action: withhold any auto-payment capability; make the only refund tool one that posts a Telegram approval request to the owner and waits; add a pre-tool hook that rejects any amount over the cap; and log the proposal, the objective it served, and the decision. The kill switch is your always-safe fallback — pull the credential and the agent instantly can't perform that action.

Build & deploy

Run, promote, maintain

A pilot is live. Now the long game: observe against your objectives, promote autonomy only on evidence, widen one step at a time — and know the kill switch cold.

Observe

Read the decision log against your objectives. Is the system advancing them, and is it explaining itself in plain language? Audit is on for exactly this — every action records which objective it served and why. If you can't tell why it did something, that's a signal, not a quirk.

Promote on evidence

When an action has been consistently right at recommend — you've been saying yes every time — promote it:

edit Governance Markdown (recommend → auto)
  → re-validate in Mission Control
  → re-compile
  → reload the engine

This is the autonomy migration the Governance and Learning layers were built for. It runs both ways: if an auto action starts disappointing, demote it with the same edit.

Widen one step at a time

The next agent, the next objective, or the next data source — but never two at once. Each addition is a small, observable change you can roll back. Growth is a sequence of confident steps, not a big-bang switch-on.

Maintain

Schedule Learning reviews and briefings via the engine's cron. And whenever you change anything, follow the same loop: edit Markdown → validate → re-compile → reload. The folder stays the single source of truth; the running system is always a reflection of it.

Kill switch — always safePausing breaks nothing; the model is just files. Three moves everyone operating this should know before go-live:
  • Pause: stop the engine's gateway / disable the agent.
  • Pull a capability: remove the tool or credential — the agent instantly can't do that thing.
  • Roll back: revert the Markdown, re-compile, reload.
That's the whole journeyUnderstand → set up → define → validate → compile → deploy → run. The Playbook has the master checklist if you want to track yourself against it.

FAQ

Quick answers to the questions that come up most.

Do I need all seven layers to start?

No. Strategy + Governance + one Domain agent is a complete first pass. The other layers can sit at status: planned and be filled in as you need them — the architecture is designed to be grown incrementally.

Do I need both the folder and the launch prompt?

Yes, and they ship together. The launch prompt (AGENTS.md) only bakes in Strategy and Governance — the things the agent must always have in mind. It reads the other layers and per-action detail on demand from the folder's files. In the download, the prompt sits inside the folder with the layers, so the folder is the one self-contained thing you run.

How do I edit a model later?

Open Mentor Studio and use Import an existing folder to load it. You can re-map, re-validate, edit any step, and recompile. The editable folder is also inside the deploy ZIP. The maintenance loop is always: edit Markdown → validate → re-compile → reload the engine.

Which AI engine does it run on?

Any. Mentor is engine-agnostic and entirely Markdown. The Engine adapters reference maps Mentor's abstract capabilities onto a real engine; Hermes Agent is the worked example. Switching engines means swapping the adapter, not rewriting your model.

Is anything uploaded to a server?

No. Studio, Mission Control, the Dashboard, and these docs all run entirely in your browser. The CLI runs on your own machine. Nothing leaves your computer.

What do the autonomy tiers mean, and where do I start?

auto = do it now and log why; recommend = propose and wait for a yes; approve = do nothing until a named person signs off. Start cautious — keep risky or irreversible actions behind approve, put new actions at recommend, and promote toward auto only on evidence.

Is this a running system or a blueprint?

The model is a blueprint — agents and objects are Markdown descriptions, and nothing executes until you bind the model to a real engine and wire it to your tools and data. The Deploy page covers exactly what turns the blueprint into a running system.

Will it replace my staff?

It isn't designed to. The aim is to cut operational noise and surface the right decisions to the right person — people stay the approvers, supervisors, and final word. See Humans in the loop.

Can I use this for something other than hospitality?

Yes — the structure is deliberately generic. Trades, logistics, clinics, retail, field services: the agents and object types change, the seven-layer shape stays the same. The repo ships one complete worked example — Riverside Café — and the same seven layers apply whatever the business.

What if validation is red?

The validation panel lists exactly what's wrong. Don't deploy until it's green — see Troubleshooting for the common causes and fixes.

Troubleshooting

The common snags, what causes them, and how to fix them — split into validation errors and deployment issues.

Validation errors

A model is valid only when every cross-layer reference resolves — not just when each file parses. The most common reds:

What you seeCause & fix
Weights don't sum to 1.0Your objective weights add up to something other than 1.0 (±tiny tolerance). Adjust them until they total exactly 1.0.
Objective missing a targetEvery objective needs ≥1 target with a valid operator (>=, <=, >, <, ==). Add a measurable target.
Approve-tier action has no approverAny approve action must name a valid approver. Add one that exists in Governance/Approvers.
serves doesn't resolveAn action references an objective id that doesn't exist. Check spelling / that the objective is defined.
escalates_to doesn't resolveAn action points to another action id that doesn't exist. Fix the reference.
Operator's fulfils_approvers unresolvedA person in the Human layer claims an approver role Governance never defined. Define the approver, or correct the id.
Object relationship unresolvedA relationship's to points at an object type that isn't defined in the Objects layer. Add the type or fix the id.
Agent action/object unresolvedAn agent lists an action or object type that doesn't exist. Trim the list or define what's missing.
Audit invariant failedlog_all_actions and require_reasoning must both be true. Leave audit on.
Soft warning, not an error"Shared action — usually one owner" means an action is assigned to more than one agent. This is allowed (some actions legitimately overlap, like guest messaging) — keep it only if it's deliberate.

SymptomLikely cause & fix

The engine talks but can't do anythingIt has the prompt but no tools/data. Behaving ≠ acting — wire the minimum tools and read-only data for the one pilot agent (Deploy).
